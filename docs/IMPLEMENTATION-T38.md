## Adoption 0.1.2 après la première publication de Lab

La branche `module/purchase-requests/t40-adoption` part du main Lab `abcd1f21f957729a811b32238584c835b5f66860`, qualifié par 1 165 tests CI. Elle installe le paquet public 0.1.2, sélectionne son reçu `manifest-0.1.2.json` et retire la candidate externe devenue version installée. Les trois compositions utilisent `versionRange: "0.1.2"` exactement, comme le solveur du plan accepté ; une plage avec `^` changerait son digest. Les trois verrous sont générés par `scripts/modules/lock.mjs` avec `--cache-validation creezio.purchase-requests`. Le cache de validation est comparé aux octets liés par le reçu public. Aucun schéma de table métier, thème, front ou module natif n'est modifié par cette adoption.

Le Site B public `https://creezio-lab.fiduciaire615016.chatgpt.site` a été publié en 0.1.0, avec synchronisation du registre, compte natif et droits admin/app. Les parcours API ont vérifié deux demandes, leur idempotence, leur révision 5 et leurs pièces jointes R2 octet exact. Le navigateur a vérifié le front, les fiches, deux tours OpenAI donnant `request-card` et `request-picker`, leurs relectures directes et la conservation du brouillon entre onglets et après rechargement. Ces preuves constituent la base avant mise à jour ; elles ne qualifient pas la publication 0.1.2.

Le contrôle préalable prévoyait de comparer les empreintes des compositions/verrous générés aux cibles natives acceptées, séparément pour Sites et Docker. Le plan local Sites donnait composition `sha256-315b9a965ec29e42e72d2b93ee7eb9beaee2441abd56f997d54d0d34e78eb9d6` et verrou `sha256-0f42527d89767bfec161dd0e9fdb3bcc01e89125fcfa0944a8b946b45a956a50`. Le plan Linux antérieur conserve sa propre référence ci-dessous. Ces empreintes décrivent la cible 0.1.2 d'alors, pas les nouveaux verrous de la branche T40.

Avant le correctif T40, le cycle natif calculait l'état effectif depuis les empreintes courantes, sans constat durable de publication ni annulation explicite. Une modification indépendante ultérieure du verrou pouvait donc bloquer un ancien plan. Le correctif adopté en source fournit confirmation et annulation motivée ; son application réelle dans Lab reste à qualifier. Ne jamais effacer les plans ou leur tête D1 pour contourner cette limite.

La branche de travail reprend le main Lab `e6e6001254442ddf272355c5dcde754f2b0a1393`, qualifié par 1 155 tests CI, puis fusionne explicitement le Core `a911e4d924b9acb3a33aeb6b57c47ae6d0e3bd06`. L'identité `creezio.lab`, le thème, le front, les dépendances publiques et les modules métier sont conservés. Les conflits de fusion portent sur les métadonnées et documents ; les verrous Lab sont régénérés avec le reçu public du module installé. Aucun workspace SDK local n'est réintroduit : SDK 1.1.0 public, contrat Core 0.0.0 et module d'achat 0.1.0 restent les versions consommées à cette étape. La version applicative devient 0.0.1 pour cette adoption.

Le raccord d'inventaire reçu de l'amont permet d'examiner une archive candidate sans la charger ni remplacer le module installé. Le module 0.1.0 présente un conflit entre sa route statique de création et sa route paramétrée de détail. Le SDK refuse explicitement les routes ambiguës ; le Starter a publié la correction dans [`module-v0.1.2`](https://github.com/creezio/Creezio-Extension-Starter/releases/tag/module-v0.1.2), depuis `3aa49c97a0802fa383c44588f835326f89bb006e`. Aucun contournement de résolution n'est ajouté au front Lab.

Le bootstrap Lab épingle et vérifie les trois fichiers publics 0.1.2 : runtime `sha256-e73d9767ea3e361ed635e91cf2d73b8a0037ee5db17503b2c45100e32fdb14ea`, validation `sha256-4d981a292862cd61b7025362ea934d11a85b9d46af9ffe31d6ef372a3b0add6f` et reçu `sha256-3386c7877b9970f9a743dc59cee2258f770cb8cd0877314bb5f31ae2bbbb50ad`. Leur reçu lie la source à `sha256-f227f7caa9ad2bf3ddaae48cd07ce2216fc6c806833c0feaef63219ddfcbedd6`. `configuration/module-inventory.json` les déclare sous `externalPackages` ; la composition, le verrou et npm continuent de sélectionner 0.1.0. Le composeur doit montrer 0.1.2 comme candidate dans Modules et extensions, sans installer son code ou migrer les données.

Une sonde sans clé dans le conteneur Linux a isolé un second défaut : Node atteint OpenAI en HTTPS, mais workerd refusait le certificat faute de magasin de confiance système dans l'image `node:24-bookworm-slim`. L'image installe désormais le paquet Debian `ca-certificates`, sans désactiver TLS. Après reconstruction, un Worker éphémère a reçu HTTP 401 JSON de `/v1/models` sans clé, sans erreur TLS ; la sonde a été disposée et le volume de données a été conservé. Cette preuve est bornée à la sortie HTTPS du Worker : elle ne prouve ni une clé OpenAI valide, ni une génération, ni la recette Site B. Le tour initial à issue inconnue sans reçu est conservé et n'est pas rejoué. La [recette Docker](../adapters/docker/README.md) décrit la reconstruction ; `CREEZIO-T37-LAB-WORKER-CA-PROBE-2026-09-28.json` conserve le rapport opérateur expurgé hors dépôt.

La prévisualisation du plan 0.1.0 → 0.1.2 a réussi en Linux Lab et son acceptation dans l'UI porte la révision 1, référence `4a3c56cb-8b77-4243-bea5-f745522d9ff3`. Elle exige encore publication et n'a pas installé 0.1.2. Trois tours OpenAI ainsi que les actions widget direct, message et contexte ont été observés dans ce profil ; la capture durable du contexte ne prouve pas son emploi par le modèle, car le même renseignement figurait dans l'historique texte.
